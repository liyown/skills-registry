# v0.6.0 Rename: skills-registry → superpower-enterprise

Date: 2026-06-10

## Goal

Rename the repository from `liyown/skills-registry` to `liyown/superpower-enterprise` and reposition the collection as "the enterprise augment layer for `obra/superpowers`", like `mybatis-plus` is to `mybatis`. Land a new meta-skill `enterprise-stack` as the single install point. 0 → 1 net skill, 0 code changes to the existing 8.

## Context

The user's directive was: "为了继续和 superpower 相符相成，以及企业里需要的技能，应该补全的能力，使得这个仓库变成一个 superpower 的企业增强版就像 mybatisplus 对于 mybatis，注意改名和安装方式". Two requirements: (a) the relationship to `superpowers` must be obvious at a glance, (b) install must be one command that pulls in both.

The previous position was a generic "collection of skills". The rename to `superpower-enterprise` makes the relationship visible in the URL itself, in the `npx skills add` examples, in the README header, and in the new meta-skill's name.

The rename is a breaking change for any consumer who has pinned to a pre-v0.6.0 tag (`#v0.3.0` – `#v0.5.0`) with the old URL `liyown/skills-registry`. GitHub's repo-rename redirect handles those pins automatically; the installed skill folders are byte-identical. New pins use the new URL.

## Key Entrypoints

- `README.md` — the repositioned top-level doc. Opens with the mybatis-plus / mybatis analogy. A new "Relationship to `obra/superpowers`" table makes the complementarity explicit per concern. The install block shows the superpower + this collection in one combined command.
- `skills/enterprise-stack/SKILL.md` — the meta-skill. ≤ 80 lines, router-shaped, references the per-skill inventory.
- `skills/enterprise-stack/prompts/inventory.md` — one-line per skill with the install command and the superpowers neighbour. Two tables: "Shipped Today" (8 skills) and "Planned" (8 skills, with the planned install line — do not run).
- `docs/rfcs/2026-06-10-enterprise-flow-skills.md` — the 8 planned skills, referenced from the meta-skill. Unchanged from v0.5.0 except the planned-install lines now use the new repo path.

## Decisions

- **Rename to `liyown/superpower-enterprise`.** The path is what consumers type into `npx skills add`. The mybatis-plus / mybatis analogy is the clearest model: the augment has its own URL, the base has its own URL, and the combined install references both.
- **Ship a meta-skill (`enterprise-stack`) in the same release.** Without a meta-skill, the "single install point" promise is just a README section. With a meta-skill, an agent that loads `enterprise-stack` gets the full inventory and the per-skill install commands in one place.
- **Do not rename the existing 8 skill folders.** The 5 `*-code-reviewer` skills, `goal-driven-development`, `project-knowledge-capture`, and `spec-doc-linter` keep their names. They are the *what*; the rename is about the *where* (repo path) and the *meta* (enterprise-stack). Renaming the skills themselves would break consumer installs and add no clarity.
- **Historical CHANGELOG / INDEX rows keep the old URL.** `## 0.3.9 (2026-06-08)` was published under `liyown/skills-registry#v0.3.9`. Editing those rows to the new URL would falsify history. GitHub's repo-rename redirect handles the legacy pins; the historical rows stay as they were.
- **`v0.6.0` is a major bump.** SemVer: a breaking change to the install URL is a major bump. The collection's existing 8 skills are not API-breaking; only the install command is. But SemVer's rule is to bump major for any consumer-affecting change, and an install URL change is consumer-affecting.
- **No GitHub-rename automation.** The user (or any repo admin) renames the repo at https://github.com/liyown/skills-registry/settings. The agent does not have permission to do that. After the rename, `git push` lands on the new path automatically. Until the rename happens, the new README's install commands will 404 on the public web.
